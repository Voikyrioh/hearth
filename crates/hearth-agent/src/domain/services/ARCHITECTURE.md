# Architecture — domain/services

Moteur de conteneurs et services (HRT-61, HRT-63, ADR-0036 à ADR-0038). Règles pures, sans E/S : ni `bollard`, ni SQLx, ni axum, ni tokio, ni lecture de `/proc`. Le moteur est vu par le port `application/ports/container_engine.rs`, le superviseur par `application/ports/service_supervisor.rs` ; ce dossier ne connaît que ses propres types. Aucun type d'ici ne porte une VALEUR de variable d'environnement ; les noms de variables et la commande ne s'y trouvent que dans `Hidden` (`Debug` masqué).

```
services/
├── engine.rs  → `EngineState` (les huit états plus `Checking`), `classify_probe` (sonde vers état : socket absent sans repère d'installation = absent, avec = arrêté, refusé = arrêté, EACCES = accès refusé, silence = ne répond pas, autre moteur = non pris en charge, API < 1.41 = version non prise en charge, désactivé sans sonde), `is_supported_engine`, `ApiVersion`, `Debounce` (au plus un changement publié par fenêtre, temps injecté) — BR-ENGINE-002, 005 à 013, 019, 021
├── state.rs   → `Observation` (un conteneur réduit à ce que la liste et le détail montrent), `derive_state` (état d'un service, fonction pure : code de sortie, `restarting`, pause, jamais démarré), `derive_supervised` et `derive_unit_state` (état d'un service supervisé : celui de l'unité quand le conteneur ne tourne pas), `stop_grace_s` (délai d'arrêt), `StartWindow` (démarrages des 10 dernières minutes, 3 = boucle ; HRT-64 : `exempt`, les démarrages demandés par Hearth ne comptent pas), `Transition` et `overlay_transition` (HRT-64 : « Arrêt en cours » et « Démarrage » montrés pendant une action de Hearth, jamais vers « En marche »), `honour_stop_request` (un arrêt demandé depuis Hearth fait d'une sortie non nulle un arrêt), `compare_names` (tri sans la casse) — BR-SVC-004 à 007, 012
├── image.rs   → `image_name` : nom, version, identifiant court ; image sans nom — BR-SVC-022
├── key.rs     → `ServiceKey` : `c_` et `u_` produites, `h_` analysée seulement — ADR-0037, BR-SVC-016
├── unit.rs    → `UnitName` (nom d'unité validé : jeu de caractères de `systemd.unit(5)`), `UnitStatus`, `UnitLookup`, `parse_show` (sortie de `systemctl show`), `parse_timespan`, `unit_of_cgroup` (groupe de contrôle vers unité), `client_refs` (ligne de commande d'un client du moteur vers les conteneurs qu'elle nomme), `is_engine_client` — BR-SVC-016
├── hidden.rs  → `Hidden` : nom de variable ou argument de commande, `Debug` masqué, pas de `Display` — BR-SVC-008
├── logs.rs    → journaux d'un service (HRT-66, BR-SLOG-*) : `LineAssembler` (octets du moteur vers lignes : fin de ligne `LF`, `CR LF` ou `CR` seul, 64 Kio bruts au plus par ligne, nettoyage et coupe à 10 000 caractères par `hearth_proto::log_text`), `split_timestamp`, `RankTracker` (curseur de reprise : heure en ms et rang ; voit une horloge qui recule) et `ResumeFilter`, `check_resume` (un curseur du client n'est cru que dans la fenêtre : `RESUME_MAX_AGE_MS`, `RESUME_MAX_LINES`, `CLOCK_SKEW_MS`, `FROM_START_LINES`), `LogRing` (anneau borné, perte comptée en `gap { slow }` pour le direct et `gap { first_page }` pour la première page, repères jamais perdus), `flush_due` (100 ms, 500 lignes, 256 Kio), `LogTarget`/`LogContainer`/`LogOrigin` (ce que la clé désigne et qui l'a créé), `Viewer` et `may_read` (le point de décision « lisible par ce compte » d'après l'origine que lui donne le filtre de `visibility.rs` : créé par Hearth, tous les comptes ; adopté, le droit de gérer les services ; non adopté, personne, comme une clé inconnue ; rejoué pendant la lecture) — BR-SLOG-011, BR-SLOG-018, BR-ADOPT-004, 015, 016
├── spec.rs    → `SpecBody` (la description durable sans secret : image, ports, montages, redémarrage, limites, réglages, fiche ; bornes `validate`), `SpecSecrets` (noms et valeurs de variables, commande, réponses d'une fiche : `Secret`, jamais affichés), `fields`/`from_fields` (un champ scellé par secret, rangs sans trou), `fold_name` ; `SpecFiche` garde la fiche, sa version, son empreinte, la variante, les réponses (`SpecAnswer`, les secrètes sans valeur en clair), les questions figées et les contrats acceptés (`SpecAgreement`) — HRT-83, HRT-101, ADR-0044, BR-EDIT-034, BR-EDIT-035, BR-FICHE-029
├── drift.rs   → `compare` : le voulu (révision courante) contre l'observé (`ObservedContainer`) : conforme, « Modifié hors de Hearth » (champs nommés), « Conteneur absent ». Constate, ne corrige rien — HRT-83, BR-EDIT-036
├── limits.rs  → bornes de tout ce qui vient d'un conteneur : `bounded` (sans caractères de contrôle, coupé à une longueur), `MAX_PORTS`, `MAX_MOUNTS`, `MAX_ENV_NAMES`, `MAX_COMMAND_ARGS`… — BR-SVC-021
├── from_fiche.rs → d'une fiche à la description d'un service (HRT-101, BR-FICHE-013, 021, 023, 024, 029) : `body_and_secrets_from` (un brouillon traduit, jugé par `OrdinaryDeployment`, devient `SpecBody` + `SpecSecrets` + `ProducedFile` ; secrets tirés sous `gen-<id>`, réponses secrètes scellées à part), `produced_file_perms` (image root : `0600` root, sinon `0640` au propriétaire de la fiche), `fit` / `fit_warnings` (un minimum MESURÉ bloque, un chiffre de l'éditeur ou non mesuré jamais)
├── delete.rs  → supprimer un service (HRT-85, BR-DEL-006 à 008) : `split_mounts` (dossiers gérés, dossiers du serveur, noms non sûrs), `fate_of` (effacer, partagé avec un autre conteneur, non vérifiable) ; fonctions pures, un doute vaut « conservé »
├── deploy.rs  → déployer une image (HRT-68, ADR-0039) : `validate` (une demande vers une `ValidDeploy` : description durable + secrets, ou un refus nommé par champ et code, jamais la valeur), `ImageRef`, `validate_name`, `check_limits` (limites obligatoires bornées par la machine), `flatten_target` (nom injectif du sous-dossier géré), `op_plan` (les cinq étapes, `create` point de non-retour) — BR-DEPLOY-002 à 007, 035, 038
├── plan.rs    → `ContainerPlan` : le plan de conteneur FERMÉ, tout ce que l'agent demande au moteur (aucun champ privilégié) ; `plan_from_spec` en est le constructeur unique, depuis la description durable ; `image_reference` ajoute `@sha256:…` quand la description épingle une empreinte (HRT-101) — ADR-0039, BR-DEPLOY-035
├── ports.rs   → qui tient un port : `verdict` (libre, tenu, réservé par un service arrêté, programme, port de l'agent), `suggest` (plus petit port libre au-dessus), `PortWorld` — BR-DEPLOY-007 à 009, BR-ADOPT-022
├── command.rs → `split_command` : la ligne de commande en arguments, sans interpréteur — BR-DEPLOY-014
├── pull.rs    → `PullTracker` : la progression d'une récupération d'image, agrégée sur les couches, jamais décroissante — BR-DEPLOY-016
└── visibility.rs → ce que Hearth publie (HRT-79, ADR-0043) : `visibility_of` (créé par Hearth, adopté ou caché ; le seul endroit qui le décide), `Adoption`, `may_read_details` (commande et noms de variables d'un adopté : le droit seulement), `lapsed` (l'adoption d'un conteneur sans unité tombe avec lui), `unit_is_gone` (l'adoption par unité tombe quand le système ne connaît plus l'unité et qu'aucun conteneur ne la porte, BR-ADOPT-017), `Holder` (qui tient un port ou un nom : un conteneur caché n'a aucune charge utile) — BR-ADOPT-001, 015, 016, 017, 022
```

Les verrous et le journal d'intention ne sont pas ici : voir `../ops/`. `folders.rs` (dossiers refusés, HRT-75) est décrit plus haut dans le code ; les tranches suivantes ajoutent la suppression et la modification d'un service.
