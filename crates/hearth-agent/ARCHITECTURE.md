# Architecture — hearth-agent

Service installé sur la machine pilotée. Hexagonal : les dépendances vont de `entrypoint` et `infrastructure` vers `application` puis `domain`, jamais l'inverse ; `entrypoint` et `infrastructure` ne se connaissent pas, seul `app.rs` (racine de composition) les assemble. `lib.rs` expose le tout (les tests d'intégration démarrent un vrai serveur) ; `main.rs` initialise les journaux, appelle `app::run` et journalise toute erreur fatale.

## Mise à jour de l'agent à distance (HRT-17)

Règles `BR-UPDATE-011` à `019` et `024`, ADR-0014, contrat `docs/open-api/agent-update.md`, runbook `docs/runbooks/mettre-a-jour-agent.md`.

- `domain/update/` : `target.rs` (`plan_update` : installation gérée, déjà en cours, cible valable : version plus récente, URL HTTPS sans identifiant, somme), `progress.rs` (`PercentTracker`), `supervise.rs` (`check_verdict` : 60 s, nouvelle version et même certificat), `record.rs` (`Job`, `SupervisorState`, `UpdateRecord` : ce que la mise à jour écrit dans `update/`, sans secret ; la version visée est `Option` : absente quand une trace illisible ne la dit pas), `orphan.rs` (`classify_orphan` : un travail laissé en cours selon la version qui tourne, dont `ForeignVersion` pour une version posée à la main), `resume.rs` (HRT-27 : `Marker`/`Phase`, le marqueur d'étape du superviseur rejouable, `enter` : début, reprise, reprises bornées, abandon, marqueur illisible ; `swap_done`, `database_copy`, `binary_restored`, `resume_phase`, `rollback_step` : l'ordre du retour arrière, base avant binaire : jamais un échange refait ni une base remise après le retour de l'ancien binaire), `space.rs` (`check_space` : assez, pas assez, impossible à mesurer = refus). `domain/install/files.rs` : **source unique des noms de fichiers** (identité, base, `update/…`, temporaires), lue par l'écriture et par la purge.
- `application/update.rs` (`UpdateService` : `start` rend `202`, tâche détachée : téléchargement en mémoire, somme, signature, dépôt, copie du superviseur, travail, lancement ; `resume` au démarrage annonce le résultat une fois ; `status`, `last`, `subscribe`) et `application/update_supervisor.rs` (`Supervisor::run`/`drive` : arrêt, échange atomique, redémarrage, contrôle, retour arrière, chacun suivi du marqueur `update/phase.json` ; rejouable après une mort, BR-UPDATE-030 à 034). - `infrastructure/update/` : `download.rs` (`HttpsDownloader` : reqwest, rustls + `ring`, TLS 1.3, magasin de certificats du système, redirections en HTTPS seulement, aucun proxy d'environnement), `minisign.rs` (`MinisignVerifier`, clé embarquée), `host.rs` (`FsUpdateHost` : dossier `update/` 0700, verrou de fichier `file_lock::HeldLock`, `systemd-run`), `feed.rs`. `infrastructure/install/probe.rs::AgentHelloProbe` (le contrôle du superviseur).
- `entrypoint/http/update.rs` (`GET /agent/update`, `GET /agent/update/last`, `POST /agent/update` en `Access::Admin`) ; sujet `update` du flux dans `entrypoint/ws/connection.rs` ; sous-commande cachée `update-supervise` (`entrypoint/cli.rs`) exécutée par `app/update.rs::run_supervisor`.
- `build_info.rs` : la version, en un seul endroit. `build.rs` embarque `update-key.pub` (ou `HEARTH_UPDATE_PUBKEY_FILE`, tests de bout en bout seulement).

## Conventions

- **Le cas d'usage rend une structure applicative ; `entrypoint/http` la convertit en type du fil de `hearth-proto`.** `application` ne connaît jamais le contrat JSON.
- La clé privée ne sort pas de `infrastructure/tls` : les ports n'exposent que du public.
- Les décisions métier sont des fonctions pures de `domain/` ; les adaptateurs observent et exécutent (ex. dernier administrateur : le dépôt compte dans la transaction, `domain::accounts::check_removal` décide).
- **Écritures atomiques, un port par sujet** : toute écriture passe par `Store::begin` → `UnitOfWork`, une transaction neutre qui couvre tous les sujets et lit, garde, écrit en une fois ; SQLite `BEGIN IMMEDIATE` sérialise les écrivains, sans `commit` tout est annulé. **Forme** : l'unité de travail ne porte aucune opération elle-même, elle donne un accesseur par sujet (`uow.accounts()`, `uow.sessions()`, `uow.login_attempts()`, `uow.operations()`) qui rend le port d'écriture du sujet (`AccountTx`, `SessionTx`…), tous liés à la même transaction. Les dépôts (`AccountRepo`, `SessionRepo`…) ne font que lire, sur le pool. Un nouveau sujet (exemple : le journal, HRT-05) = un fichier de ports (`*Repo` + `*Tx`), un accesseur sur `UnitOfWork`, une implémentation dans `infrastructure/sqlite/{sujet}.rs` ; aucun autre sujet n'est touché. Un cas d'usage n'importe que les ports des sujets qu'il touche. Un seul chemin par opération (fermer des sessions : `SessionTx::close`, qui retient aussi les empreintes révoquées). Exemple : la connexion écrit le compteur, la session et `last_login_at` dans une seule transaction.
- **Dossier de données** : `infrastructure/data_dir.rs` est le seul endroit qui le crée (absent : créé en 0700 ; existant et ouvert aux autres : erreur qui dit de faire `chmod 700`, sauf dossier vide dont on est propriétaire, resserré ; jamais de chmod silencieux sur un dossier qu'on n'a pas créé) et qui rend `hearth.db` privé (0600, `-wal` et `-shm` suivent) ; sous Windows il crée seulement le dossier, sans contrôle de droits (développement) ; `app.rs` l'appelle avant la base et le magasin d'identité.
- **Dates en base** : texte UTC à largeur fixe `YYYY-MM-DDTHH:MM:SS.mmmZ`, triable ; écriture et lecture faillibles (`StoreError`). L'horloge (`infrastructure/clock.rs`) tronque à la milliseconde, une seule fois : la date rendue par une écriture est celle qu'on relit.
- Les cas d'usage ne rendent jamais le haché du mot de passe (`AccountView`).
- **Contrôle d'accès** : une seule couche (`entrypoint/http/auth.rs::guard`). **Toute route est une ligne de `ENDPOINTS`** (`entrypoint/http/mod.rs`) : méthode, chemin, niveau d'accès (public, authentifié, administrateur), suivie ou non par clé d'opération, action de journal d'activité. Le routeur est construit depuis la table et pose lui-même, par route, la couche d'accès (session, puis rôle via `Role::can_manage_accounts`) et le suivi : un handler ne redéclare rien, il reçoit l'appelant par l'extracteur `Caller`. `tests/http_api.rs` parcourt la table et vérifie le comportement réel (sans jeton `401`, lecture seule `403`, rien ne change en base, `405` pour toute méthode non déclarée d'un chemin connu). Ce qui est garanti : `router()` ne crée de route que depuis la table, donc une route y figure avec un niveau, et ce niveau est appliqué par le routeur. Ce qui ne l'est pas : un chemin entièrement nouveau ajouté en contournant la table (le test ne couvre que les chemins de la table) ; la relecture de revue reste le garde-fou.
- **Connexion** : identifiant inconnu et mot de passe faux suivent le même chemin (vérification Argon2 contre un haché factice, échec compté, même transaction) ; la comparaison des empreintes de jetons est en temps constant ; l'adresse du client vient de la connexion TCP, jamais d'un en-tête.
- **Version d'interface** (`X-Hearth-Api`) contrôlée sur toutes les routes sauf `/hello` ; **clés d'opération** (`Idempotency-Key`) : colonne « suivie » de `ENDPOINTS` (requêtes authentifiées qui modifient, pas la connexion dont le résultat contient un jeton). Une clé est celle d'un compte, liée à la requête (méthode, chemin, SHA-256 du corps) ; la requête suivie s'exécute dans une tâche détachée (un client qui coupe ne perd pas le résultat) ; au démarrage, les opérations restées en cours deviennent « interrompues ».
- **Charge** : les calculs Argon2 sont plafonnés (permis = min(cœurs, 4), file de 32, au-delà `503 BUSY`) ; les connexions d'une même adresse sont traitées l'une après l'autre (huit en attente au plus, la suivante reçoit `429 TOO_MANY_ATTEMPTS` tracé en `warn`), dans une tâche détachée (un client qui coupe n'empêche pas de compter l'échec) ; le permis Argon2 vit dans la closure bloquante, rendu à la fin du calcul même si l'appelant est abandonné.
- **Mesures** : la sonde (`SystemProbe` + `GpuProbe`) observe, `domain::metrics` décide (anneau, fenêtres, moyennes). Une mesure illisible est un champ absent, jamais un zéro inventé, et n'affecte pas les autres ; matériel absent = capacité fausse et liste vide, jamais une erreur. L'échantillonneur (`tasks::spawn_sampler`, 1 Hz) n'est arrêté ni par une erreur ni par une panique de sonde (`spawn_blocking` convertit la panique en erreur de ce passage). Les sondes s'exécutent sur un fil bloquant : aucune lecture du système dans le runtime. Les fenêtres et l'ordre reposent sur l'horloge monotone (`MonotonicClock`), la murale ne date que l'échantillon. Une sonde qui ne répond pas en 2 s : échantillon abandonné, tours sautés jusqu'à son retour (`Flight` : un seul appel en cours), identité servie depuis le cache (30 s). `nvidia-smi` : trouvé par `HEARTH_NVIDIA_SMI`, `PATH`, chemins connus ; tué puis relancé s'il se tait 10 s ; la carte reste dans l'identité pendant la relance. Un échantillon coûte moins de 5 ms hors `nvidia-smi` (cible Linux ; sous Windows l'énumération des interfaces réseau y ajoute une douzaine de ms, dev seulement).
- **Flux temps réel** : `/stream` est une ligne de `ENDPOINTS` d'accès `FirstMessage` (le routeur ne pose pas de couche d'accès : l'authentification est le premier message du flux, contrôlé par `SessionService::authenticate` ; la version d'interface est contrôlée sur la requête d'ouverture). Chaque connexion est une tâche ; les échantillons passent par `tokio::sync::broadcast` borné (un abonné lent perd des échantillons, il ne bloque personne ; un message qui ne part pas en 10 s fait abandonner le client). Le `snapshot` est précédé de l'abonnement au canal, puis `domain::stream::is_new` écarte ce que le snapshot contient déjà. La session est revérifiée toutes les 5 s. À l'arrêt, `ServerHandle::on_shutdown` ferme les flux (1001) avant d'attendre les connexions. Quotas : connexions pas encore authentifiées (2 par adresse, 16 au total, prises à l'ouverture, rendues à l'`auth` ou à la fermeture) distincts des flux authentifiés (32 au total, 4 par compte, pris après `auth`) ; un `subscribe` par seconde et par connexion ; nouveau `snapshot` quand une carte graphique apparaît (cache d'identité invalidé par un changement de la liste des cartes, jamais de verrou tenu pendant la sonde, pas de nouvelle tentative avant 5 s) ; le rôle est relu avec la session (`Role::can_read_audit`). Le sujet `audit` passe par le port `AuditFeed` (l'événement de journal du domaine, converti vers le fil dans `entrypoint/ws`) ; le rôle suit la règle unique `Role::can_read_audit` (`domain::audit::can_read_journal`). L'identité de la machine est lue une fois avant de servir (`MetricsService::warm_up`) et la détection des cartes graphiques se fait hors du runtime asynchrone, gardée 5 s.
- **Tâches de fond** : `entrypoint/tasks.rs` ; un passage qui échoue ou panique est journalisé et le suivant a lieu ; elles s'arrêtent avec `RunningAgent`.
- **Journal d'activité** (`domain/audit/`) : **aucun secret ne peut entrer dans un événement, par la forme des types** (aucun champ de texte libre : compte = `Username`, action/résultat/raison = énumérations à texte fixe, cible = compte ou motif de route statique, origine = adresse de la connexion et nom du poste nettoyé). L'identifiant saisi lors d'une connexion refusée n'est jamais retenu (ce peut être un mot de passe). **Qui écrit quoi** : les cas d'usage écrivent le succès dans la transaction de l'action (`uow.audit()` via `application/audit.rs::Pending`), puis publient sur `AuditFeed` après validation (**les connexions refusées** passent par `AuditSink` comme les autres refus, jamais une par une) ; la couche d'accès écrit, par `AuditSink` hors transaction, les refus faute de droits (consultations comprises) et les échecs des requêtes qui modifient, d'après la colonne `audit` de `ENDPOINTS` (un handler n'y pense pas ; une réponse rejouée depuis sa clé d'opération n'écrit rien). Une erreur d'écriture dans la transaction la fait échouer (pas d'action validée sans son entrée) ; hors transaction, tracée en `error`. L'entrée écrite n'est jamais modifiée (déclencheur SQL) ; seule la purge supprime (90 jours, puis 50 000 entrées) : horaire, par lots dans des transactions à part, et déclenchée aussi toutes les 500 entrées écrites (`AuditTrail`, qui rappelle `MaintenanceService::purge_journal`, seul endroit qui purge) ; les synthèses du regroupement en attente sont écrites à l'arrêt. La recherche plein texte reçoit la saisie comme du texte (chaque mot entre guillemets) ; la requête de lecture est vérifiée à la compilation, sans SQL construit.
- **Secrets** : mots de passe et hachés sont des `Secret` (pas de `Display`, `Debug` masqué, effacés à la libération) ; aucun message d'erreur ni journal ne les contient.
- **SQLx hors ligne** : les `query!` sont vérifiées contre `.sqlx/` ; voir « SQLx » dans `CLAUDE.md` pour régénérer après toute modification de requête ou de migration.
- Les ports sont consommés en `Arc<dyn Port>` / `&dyn Port` : seul `app.rs` connaît les types concrets.

## Pour ajouter une table ou une requête

1. Migration `migrations/NNNN_nom.sql` (jamais modifier une migration déjà publiée).
2. Fichier de ports dans `application/ports/` (`*Repo` en lecture, `*Tx` en écriture), accesseur sur `UnitOfWork`, adaptateur dans `infrastructure/sqlite/{sujet}.rs`, requêtes `query!`.
3. Régénérer `.sqlx/` (voir `CLAUDE.md`), committer le dossier.

## Pour ajouter une route

1. Types de corps dans `hearth-proto/src/api/`.
2. Cas d'usage dans `application/` (ports si besoin), règles dans `domain/`.
3. Handler dans `entrypoint/http/{route}.rs` (`Caller` pour lire l'appelant ; conversion vers le type du fil dans `wire.rs`), **une ligne dans `ENDPOINTS`** (`mod.rs`) avec son accès, son suivi et son action de journal (`audit`) ; erreurs via `ApiError` (`error.rs`).
4. Fiche `docs/open-api/{route}.md` et ligne d'index ; fiche `docs/business-rules/BR-*` si règle.
