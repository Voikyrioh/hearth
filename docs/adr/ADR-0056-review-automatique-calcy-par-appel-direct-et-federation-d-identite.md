# ADR-0056 : Review automatique « Calcy »

> Brouillon du 09/10, repris et durci le 13/10, puis corrigé le 14/10 après la review de la PR 90 (barrière réelle, sortie du modèle, coût). Il portait le numéro 0035, déjà pris par la décision sur les mises à jour servies par `hearth.voikyrioh.fr`.

## Contexte
Le propriétaire veut un premier regard automatique sur ses propres pull requests : un commentaire qui relit le diff (sécurité, tests, cohérence de la doc, texte de l'interface), dans la voix d'un relecteur nommé Calcy (professionnel, de petits emoji de flamme, des jeux de mots sur le feu seulement quand le contexte les rend évidents, aucun nom ni réplique tirés d'une œuvre existante). Le dépôt est PUBLIC : le flux ne doit contenir aucun secret, ne doit jamais s'exécuter pour le compte d'une autre personne, et ne doit pas pouvoir faire dépenser de l'argent sans l'accord du propriétaire.

## Décision
1. **Appel direct à l'API Messages** (`POST /v1/messages`) depuis un script Node sans dépendance (`.github/scripts/calcy-review.mjs`), et non l'action officielle de Claude Code, dont l'usage n'est pas couvert par les crédits d'API mensuels du propriétaire (https://support.claude.com/en/articles/17154008-monthly-api-credits-for-max-and-team-plans). Aucune action tierce hors `actions/checkout`, épinglée par empreinte comme `ci.yml`.
2. **Fédération d'identité, aucune clé d'API.** Workload Identity Federation (https://platform.claude.com/docs/en/manage-claude/workload-identity-federation, https://platform.claude.com/docs/en/manage-claude/wif-providers/github-actions). Le flux demande à GitHub un jeton OIDC d'audience `https://api.anthropic.com`, l'échange (`POST /v1/oauth/token`, grant `urn:ietf:params:oauth:grant-type:jwt-bearer`, plus règle, organisation, compte de service et espace de travail) contre un jeton d'accès `sk-ant-oat01-…` de courte durée, puis appelle l'API. Les identifiants de la fédération (`fdrl_`, `svac_`, `wrkspc_`, organisation) ne sont écrits dans AUCUN fichier du dépôt : ce sont des variables du dépôt (`CALCY_FEDERATION_RULE_ID`, `CALCY_ORGANIZATION_ID`, `CALCY_SERVICE_ACCOUNT_ID`, `CALCY_WORKSPACE_ID`). Ce ne sont pas des secrets (une variable apparaît dans l'en-tête d'étape du journal d'une exécution, public pour un dépôt public) : leur confidentialité n'est pas ce qui protège. Les jetons sont masqués (`::add-mask::`) et jamais affichés. Un `ANTHROPIC_API_KEY` ne doit exister nulle part (il passerait avant la fédération).
3. **La barrière est la règle de fédération, liée au flux réutilisable de `main`.** Sur un `push`, GitHub exécute le flux du commit poussé : tout ce qui est écrit dans un fichier de flux (filtre d'acteur, `branches-ignore`, `if:`) peut être réécrit par quiconque pousse une branche, et ne protège donc de rien. Le travail sensible est dans `.github/workflows/calcy-reusable.yml` (`on: workflow_call`), appelé par `.github/workflows/calcy-review.yml` (déclencheur `push`) PAR RÉFÉRENCE À `main` (`uses: Voikyrioh/hearth/.github/workflows/calcy-reusable.yml@main`, jamais `./…`). La revendication OIDC `job_workflow_ref` vaut alors `Voikyrioh/hearth/.github/workflows/calcy-reusable.yml@refs/heads/main` quelle que soit la branche poussée (documentation OIDC de GitHub : « for jobs using a reusable workflow, the ref path to the reusable workflow »). La règle de fédération n'accepte que : sujet `repo:…:ref:refs/heads/*`, audience, `event_name=push`, `repository`, `repository_owner`, `repository_owner_id`, `actor_id` (identifiant numérique, pas le nom) et `job_workflow_ref` exact. Une règle Anthropic sait contraindre toute revendication de premier niveau par valeur exacte (`claims`) ou par expression CEL (`condition`) : référence WIF, « Rule matching semantics ». Une branche qui réécrit le déclencheur obtient un jeton de GitHub, pas d'Anthropic. Le déclencheur est `push` et jamais `pull_request` ni `pull_request_target`. Les `if:` des deux fichiers (propriétaire, dépôt, pas un fork, `CALCY_MODEL` posée) servent à économiser des minutes de CI ; celui du flux appelé, qui vient de `main`, est fiable, mais la règle reste la barrière.
   - **Repli** si la console n'accepte pas `job_workflow_ref` ou `actor_id` : environnement GitHub `calcy` avec relecteur obligatoire et branches limitées, déclaré par le job appelé, règle liée au sujet exact `repo:…:environment:calcy` (forme documentée des deux côtés). Détail dans le runbook.
   - **Conditions de validité** : la règle est posée comme dit au runbook ; `main` est protégée (PR obligatoire, relecture du propriétaire du code sur `.github/`) ; l'essai négatif a été fait (une branche qui appelle le flux par une référence locale n'obtient pas de jeton). Tant que la règle large du 09/10 existe, elle est désactivée.
4. **Le code exécuté vient de `main`, jamais de la branche relue.** Dans le flux appelé : `trusted/` (branche `main`, uniquement `.github/scripts` et `.github/calcy`) pour le script et les consignes ; `untrusted/` (le commit poussé, historique complet) lu comme donnée par `git diff`. Rien de `untrusted/` n'est exécuté (ni script, ni build, ni test, ni hook : pas d'identifiants de dépôt conservés). Le diff est lu fichier par fichier, avec les noms donnés par `git diff --name-status -z` et l'option `--attr-source=<branche de base>` : les attributs git (`.gitattributes`) de la BASE décident, pas ceux de la branche relue, qui pourrait sinon déclarer `*.rs -diff` et faire passer tout le Rust pour des binaires non relus (essai fait dans un dépôt jetable, voir les tests). Pas de pilote de diff externe, pas de conversion de texte, et `git` tourne avec un environnement minimal (ni jeton GitHub, ni identifiants OIDC, ni configuration utilisateur ou système). Il faut git 2.40 ou plus ; sinon le job échoue.
5. **Le contenu de la PR est une donnée hostile.** Titre, description, noms de fichiers, messages de commit et diff ne sont jamais placés dans une ligne `run:` ni dans une expression : seuls le sha, le dépôt, le nom de branche (en `env:` et dans le nom du groupe de concurrence, jamais dans une ligne de shell) et des variables du dépôt passent. Dans le message envoyé au modèle, ils sont encadrés par des balises à marqueur aléatoire (impossible à refermer depuis le diff), les consignes (`system`) interdisent de leur obéir, et les caractères de contrôle, bidirectionnels et invisibles en sont retirés (le commentaire dit combien). Les noms de fichiers sont nettoyés et ne sont jamais écrits dans les journaux d'exécution.
6. **Le modèle ne peut rien faire d'autre qu'écrire un texte, et ce texte n'est jamais du Markdown.** Aucun outil n'est déclaré, aucune action n'est lue dans la réponse. Une liste noire dans du Markdown a été contournée (fausse clôture, bloc dans une liste, code en ligne déséquilibré, liens par référence, adresses sans schéma, entités, références) : elle est remplacée par une construction qui ne dépend pas de ce que le modèle écrit. Le texte, après retrait des caractères de contrôle, bidirectionnels et invisibles et bornage (20 000 caractères), est posté comme TEXTE BRUT dans UN bloc de code clôturé, à la racine du commentaire, avec une clôture d'accents graves PLUS LONGUE que toute suite d'accents graves du texte (calculée). Dans un bloc de code clôturé, le contenu est littéral (CommonMark 0.31, « Fenced code blocks ») : ni HTML, ni lien, ni image, ni entité, ni mention, ni référence ne sont interprétés ; et aucune ligne du texte ne peut fermer le bloc puisqu'une clôture fermante exige au moins autant d'accents graves que l'ouverture. Par défense en profondeur, pour un robot qui lirait le corps brut : un espace de largeur nulle est inséré après `@`, après `#` suivi d'un chiffre, après `GH-` suivi d'un chiffre, et avant un `/` de début de ligne. Les lignes longues sont coupées à 100 caractères. Tout le reste du commentaire est écrit par le script : marqueur, ligne fixe, section « non lu », pied (sha validé en hexadécimal, modèle validé, nombres). La ligne fixe du script, en tête, dit : relecture automatique, avis seulement, peut se tromper, ne vaut pas approbation, n'est pas une condition de fusion. Le script ne retrouve pour la mise à jour que le commentaire du compte `github-actions[bot]` portant le marqueur.
7. **Coût borné, honnêtement.**
   - Modèle lu dans la variable de dépôt `CALCY_MODEL` (jamais écrit dans un fichier ; format contrôlé) ; variable absente : le flux ne démarre pas.
   - Diff relisable limité à 200 000 caractères (`CALCY_MAX_DIFF_CHARS`) : au-delà, un commentaire le dit, AUCUN appel.
   - **Plafond en jetons** : avant l'appel payant, le script fait compter par l'API les jetons du message exact (`POST /v1/messages/count_tokens`, gratuit, couvert par la portée de la règle ; https://platform.claude.com/docs/en/build-with-claude/token-counting). Au-dessus de `CALCY_MAX_INPUT_TOKENS` (60 000 par défaut) : avis, aucun appel payant. La documentation donne ce compte pour une estimation (écart faible possible) : plafond pratique, pas preuve au jeton près. Échec du comptage : échec du job, jamais d'appel à l'aveugle.
   - Sortie : `max_tokens` fixé à 4 000. Un seul appel par poussée, sans nouvelle tentative ; un nouveau push de la même branche annule l'exécution précédente (déclarée dans le flux appelé : le même groupe dans l'appelant et l'appelé se bloquerait) ; délai du job 10 minutes ; délai propre sur chaque appel réseau ; aucun cache.
   - Pied du commentaire : sha, modèle, jetons FACTURÉS renvoyés par l'API (entrée et sortie), jetons comptés avant l'appel, et le coût calculé avec les prix configurés (`CALCY_PRICE_INPUT_PER_MTOK`, `CALCY_PRICE_OUTPUT_PER_MTOK`) s'ils sont posés.
   - Garde contre les boucles : un commentaire ne déclenche rien (le flux ne réagit qu'à `push`) ; les branches de robots (Dependabot) et tout acteur autre que le propriétaire sont ignorés.
   - Le seul plafond qui coupe tout, script contourné compris, est celui de l'espace de travail `hearth-ci`, à poser et constater dans la console.
8. **Permissions du jeton GitHub** : aucune par défaut (`permissions: {}` dans les deux fichiers). Le job appelant accorde `contents: read`, `pull-requests: write` et `id-token: write` (nécessaire à la fédération, et à accorder côté appelant) ; le job appelé les reprend à l'identique, il ne peut pas en avoir plus.
9. **Échec** : si l'échange, le comptage ou l'appel échoue, le job échoue avec le code HTTP, le type d'erreur et le `request_id` (jamais un jeton), sans commenter la PR.
10. **Commentaire seul.** Aucune approbation, aucune fusion, aucune modification de code.
11. **Fichiers soustraits à la relecture** (verrous, images, binaires, instantanés de test, au-delà de 400 fichiers, fichiers trop gros) : le commentaire en liste les NOMS (assainis, au plus 30, dans un bloc de texte brut) avec la raison, et le modèle les reçoit aussi pour ne pas conclure sur ce qu'il n'a pas vu. Plus aucun dossier n'est soustrait à cause de son nom.

## Menaces et parades
| Menace | Parade |
|---|---|
| Quelqu'un qui peut pousser une branche (collaborateur en écriture, application ou jeton avec droit `workflows`, propriétaire qui pousse sans le vouloir le contenu d'un fork) écrit son propre flux et demande un jeton | La règle de fédération n'accepte que `job_workflow_ref` = flux réutilisable de `main`, `actor_id` du propriétaire, `event_name=push`, branche du dépôt. Un autre flux n'obtient pas de jeton d'Anthropic. Repli : environnement protégé. Protection de `main` obligatoire. |
| PR d'un fork | Pas de `push` dans ce dépôt, donc le flux ne démarre pas ; aucun déclencheur `pull_request` ni `pull_request_target` ; la règle exige `event_name=push` et le dépôt. |
| Code de la PR exécuté avec accès à l'identité | Script pris sur `main` ; la branche relue n'est que lue par `git diff` ; pas de `pull_request_target`. |
| La branche masque du code à la relecture (`.gitattributes`, noms de fichiers, dossiers) | Attributs de la base (`--attr-source`), noms listés dans le commentaire, exclusions réduites aux extensions, verrous et binaires réels. |
| Injection d'instructions dans le diff, le titre, la description | Données encadrées par un marqueur aléatoire, consignes `system` qui l'interdisent, aucun outil donné au modèle, invisibles retirés, sortie postée comme texte brut. Reste possible : un verdict ou un conseil faussé (voir Limites). |
| Injection de commande de flux ou de shell par un nom de fichier ou de branche | Aucune valeur d'auteur dans `run:` ; noms nettoyés et absents des journaux ; ligne de journal toujours sur une seule ligne. |
| Fuite par la sortie du modèle (image distante, lien, mention, commande `/…`, HTML, entité, référence) | Texte brut dans un bloc clôturé qui ne peut pas être refermé (point 6) ; le reste du commentaire est du texte du script. |
| Dépense incontrôlée (gros diff, boucle, poussées en rafale) | Plafond de caractères puis de jetons comptés par l'API, sortie fixée, un appel par poussée, annulation des exécutions périmées, délais, plafond de dépense de l'espace de travail à poser à la main. |
| Jeton OIDC ou d'accès volé dans les journaux | Masqués dès réception, jamais imprimés ; durée de vie réglée à 300 s sur la règle. |
| Hausse de privilège du compte de service | Portée `workspace:inference` si la console la propose (sinon `workspace:developer`, même accès qu'une clé d'espace de travail). |
| Un faux « APPROUVER » obtenu par injection est pris pour une approbation | Ligne fixe du script en tête : avis seulement, ne vaut pas approbation ni condition de fusion. |

## Alternatives écartées
- **Action officielle de Claude Code** : non couverte par les crédits d'API mensuels du propriétaire.
- **Clé d'API en secret du dépôt** : un secret à garder, à faire tourner, qu'un flux détourné pourrait lire. Repli seulement si la fédération devenait indisponible ; non mis en service.
- **`pull_request` / `pull_request_target`** : la règle de fédération les refuse ; `pull_request_target` donnerait en plus des droits en écriture et des secrets à du code non fiable.
- **Filtre d'acteur dans le flux comme protection** : écarté, une branche réécrit le flux (le filtre ne sert qu'à économiser des minutes).
- **Liste noire ou liste blanche de constructions Markdown reconstruites** : écartées au profit du bloc de code, plus simple et qui ne dépend d'aucune analyse du texte du modèle ; le prix est une réponse affichée en police fixe, sans mise en forme.

## Limites
- Calcy ne lit que le diff : il n'exécute rien, ne voit pas le reste du dépôt, peut se tromper ou manquer un défaut. Il ne remplace ni la CI (fmt, clippy, tests, `br-check`) ni la revue humaine.
- Une injection réussie peut fausser le verdict ou le contenu du texte du modèle ; elle ne peut ni agir, ni publier autre chose que du texte brut dans le bloc. Le commentaire est un avis, jamais une décision ni une condition de fusion.
- Le contenu du diff part chez l'API : ne jamais pousser de secret, même pour « voir ce que Calcy en dit ». Les branches poussées dans un dépôt public sont de toute façon publiques.
- Le plafond d'entrée est le comptage de l'API (estimation officielle) ; la sortie peut contenir du raisonnement qui consomme les 4 000 jetons (non essayé sur le modèle retenu).
- La barrière repose sur la règle posée dans la console et sur la protection de `main` : ni l'une ni l'autre n'est vérifiable depuis ce dépôt.
- Non vérifiable sans mise en service : que la console accepte `job_workflow_ref` et `actor_id` comme revendications, l'échange réel depuis le flux appelé (essai manuel du 09/10 réussi sur une branche jetable, pas sur ce flux), la disponibilité de `vars` dans le flux appelé, la version de git du runner, le rendu réel par GitHub des cas hostiles (la construction repose sur la spécification CommonMark, les tests lisent les blocs avec les règles de la spécification, pas avec GitHub).

## Comment le couper
- Tout le flux : `gh workflow disable calcy-review.yml` (se réactive par `gh workflow enable`).
- Sans désactiver : `gh variable delete CALCY_MODEL` (le job ne démarre plus).
- Un commit : `[skip calcy]` dans le message du dernier commit poussé ; une PR : la passer en brouillon.
- Côté Anthropic, le plus sûr : désactiver la règle de fédération ou le compte de service.

## Vérification
- Tests, sans réseau ni jeton (Node 20 ou plus, aucune dépendance) : `node --test .github/scripts/calcy-review.test.mjs`. Ils rejouent un par un les contournements de la review de la PR 90, des cas de mentions, entités, commandes, références, caractères invisibles, un essai aléatoire déterministe de la propriété « un seul bloc, rien dehors », et un dépôt git jetable pour l'effet de `.gitattributes`.
- Essai à blanc : `node .github/scripts/calcy-review.mjs --dry-run --diff .github/calcy/exemples/exemple.diff --review .github/calcy/exemples/exemple-review-hostile.md` affiche le découpage du diff, les fichiers soustraits, et le commentaire tel qu'il serait posté pour la review d'exemple, conçue pour contenir tous ces cas.
- Essais en conditions réelles, négatif puis positif : runbook, étapes 6 et 7.
