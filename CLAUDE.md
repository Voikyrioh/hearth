## Commandes

```sh
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Les trois doivent passer avant tout commit.

Les tests créent leurs dossiers temporaires sous `target/hearth-test-tmp/` (aide `crates/hearth-agent/tests/support/tmp.rs`, jamais `tempfile::tempdir()` direct), pas dans `%TEMP%`. Après une suite complète, `cargo xtask test-tmp-check` doit dire que rien n'est resté (`--clean` supprime les restes d'une suite interrompue ; la CI l'exige).

### Client Windows (`apps/desktop`)

La crate Tauri `hearth-desktop` est membre du workspace mais **hors `default-members`** : sous Linux elle ne compile pas (bibliothèques WebView absentes). Sous Linux, ajouter `--exclude hearth-desktop` aux commandes `--workspace` (le job Linux de la CI le fait) ; le job `desktop` de la CI (Windows) la vérifie. Sous Windows les trois commandes ci-dessus couvrent tout, **mais** `cargo clippy`/`cargo test --workspace` compilent la coquille Tauri, qui lit `apps/desktop/dist` à la compilation : sur un clone neuf, construire le front une fois d'abord (`cd apps/desktop && npm ci && npm run build`), sinon la compilation échoue. Pour tester seulement l'agent, sans le client ni le front : `cargo test --workspace --exclude hearth-desktop` (idem pour clippy).

```sh
cd apps/desktop
npm ci
npm run lint && npm run typecheck && npm test     # Biome, vue-tsc, Vitest
npm run build                                     # requis avant clippy/test Rust de la coquille (dist/ lu à la compilation)
npm run tauri dev                                 # application complète ; régénère src/bindings.ts
npm run tauri build                               # installateur NSIS dans target/release/bundle/nsis/
```

`src/bindings.ts` est généré (tauri-specta) et versionné ; s'il est périmé, `cargo test -p hearth-desktop` échoue : `HEARTH_REGEN_BINDINGS=1 cargo test -p hearth-desktop`. Détails et ajout d'une commande : `docs/adr/ADR-0010-dependances-client.md`.

## SQLx (requêtes vérifiées, mode hors ligne)

Les `query!`/`query_as!` sont vérifiées à la compilation contre `.sqlx/` (versionné). Sans `DATABASE_URL`, `cargo build` et la CI lisent ce dossier : rien à configurer. Après toute modification d'une requête `query!` ou d'une migration, régénérer et committer `.sqlx/` :

```sh
export DATABASE_URL="sqlite://$PWD/target/sqlx-dev.db"     # base de dev jetable ; sous Windows, chemin du type sqlite://J:/.../target/sqlx-dev.db
cargo sqlx database create && cargo sqlx migrate run --source crates/hearth-agent/migrations
cargo sqlx prepare --workspace -- --all-targets
git add .sqlx
```

Si `cargo sqlx` manque ou n'a pas le pilote SQLite : `cargo install sqlx-cli --no-default-features --features sqlite,rustls`. Voie sans le CLI : créer la base en exécutant le SQL des migrations (par exemple avec le module `sqlite3` de Python), puis `DATABASE_URL=… SQLX_OFFLINE_DIR=$PWD/.sqlx cargo build -p hearth-agent --all-targets` après avoir touché `crates/hearth-agent/src/lib.rs` pour forcer la recompilation. Les migrations déjà publiées ne se modifient jamais : on en ajoute une.

## Moteur de conteneurs (HRT-61)

L'agent lit le moteur de conteneurs (Docker) par son socket Unix et diffuse la liste des services (ADR-0036 à ADR-0038) ; ses SEULES écritures dans le moteur sont démarrer, arrêter et redémarrer un service (HRT-64, section plus bas) et, pour la suite d'arrêt d'un serveur de jeu, UNE ligne littérale de fiche sur l'entrée de son conteneur (HRT-103, `send_stdin_line`). Réglages : `[engine] enabled` et `[engine] socket` de `agent.toml`, `HEARTH_ENGINE=off` (désactive : le socket n'est jamais ouvert), `HEARTH_ENGINE_SOCKET`. Aucun moteur sur le poste de développement : tout se teste contre le faux moteur (`FakeEngine`) et un faux démon HTTP local ; le vrai moteur n'existe qu'en CI (job `engine`, `HEARTH_TEST_ENGINE=1 cargo test -p hearth-agent --test engine_real -- --ignored`). **Images des tests (HRT-168)** : `busybox:1.36` et `registry:2` sont fixées par empreinte dans `.github/scripts/test-image.sh`, appelé par l'action `.github/actions/test-image` (jobs `engine` et `engine-logs-long`) : démon, sinon archive `docker save` du cache `actions/cache` (clé = hash de `test-image.digests`, sauvé juste après la préparation, même job rouge), sinon téléchargement par empreinte chez ECR puis Docker Hub (`::notice::` au repli). Le script lance un registre local `localhost:5000` alimenté en busybox ; la suite de contrat y récupère son image (`HEARTH_TEST_PULL_REPO=localhost:5000`, défaut : ECR) : aucun quota public pendant la suite. Un registre KO sort en `REGISTRE ...` avec sa dernière erreur, jamais en échec de test. Changer l'image = changer l'empreinte dans `test-image.digests` (la clé du cache suit) et `IMAGE` de `engine_real.rs` / `engine_supervised.rs`. Tests bridés : `cargo test -p hearth-agent -j 2 --test services_https -- --test-threads=2`. **Publication (HRT-79, ADR-0043, `BR-ADOPT-*`)** : l'agent lit TOUS les conteneurs mais ne publie que les services créés par Hearth (`h_`) et les services adoptés (table `adopted_services`, migration `0011`, écrite par `ServiceAdoption`, HRT-80 : `POST /services/adopt` et `POST /services/{key}/release`, `GET /services/external` pour les candidats ; réglage `[services] adoption`, `HEARTH_SERVICES_ADOPTION=off` ; aide de test `Env::adopt`) ; les autres sont comptés (`engine.external_count`). Le filtre est `ServicesRegistry::publish` (`domain/services/visibility.rs::visibility_of`), appelé à un seul endroit : ne jamais lire `inner.containers` pour répondre à un client ni logguer un nom/une image/un port/une unité d'un conteneur (test sentinelle `tests/services_https.rs`). Aucune valeur de variable dans les types du fil sauf la réponse de `GET /services/{key}/env` (comptes qui ont le droit « gérer les services », indépendant du rôle et absent par défaut, `Access::Services`, ADR-0041, migration `0010` ; `Concealed`, consignée) ; les noms de variables et la commande (détail d'un service, HRT-63) sont dans `Hidden`/`Concealed` et ne vont dans aucune trace. Services lancés par une unité systemd (clé `u_`) : `ServiceSupervisor` (détection par `/proc` + `systemctl show`, ordres `systemctl start|stop|restart` depuis HRT-64), migration `0009` ; l'étape CI `supervised` (`tests/engine_supervised.rs`, root) consigne ce que fait un arrêt par l'API du moteur sur un conteneur d'unité.

Journaux d'un service (HRT-66, ADR-0038) : `GET /services/{key}/logs` est un WebSocket par lecture (jamais `/stream`), 1 000 dernières lignes puis le direct, anneau borné par lecture, dix lectures au plus, reprise par curseur (heure en ms et rang), suivi de la CLÉ du service d'un conteneur à l'autre. Le texte d'une ligne est du contenu sensible : aucune trace, aucun `Debug`, jamais stocké (test sentinelle `tests/service_logs_ws.rs`). Nettoyage et coupe : `hearth_proto::log_text` seulement. Lecture du moteur écrite à la main (`infrastructure/engine/logs.rs`), pas `bollard::logs`. « Ce compte lit ce service » : `domain::services::logs::may_read(viewer, target)`, un seul point (reçoit le compte et l'origine du service, rejoué pendant la lecture ; HRT-76 et HRT-79 y ajouteront leurs règles). Règles `BR-SLOG-*`. Tests bridés : `cargo test -p hearth-agent -j 2 --test service_logs_ws -- --test-threads=2`.

## Description durable des services et journal des opérations (HRT-83)

Pour un service créé par Hearth, la base de l'agent garde une description numérotée (`service_specs`) dont les secrets (noms et valeurs de variables, commande, réponses secrètes d'une fiche) sont **scellés** valeur par valeur (ChaCha20-Poly1305 de `ring`, nonce neuf par scellement, données associées = service, révision, champ) avec la clé `services.key` du dossier de données, créée à la première nécessité, jamais régénérée par-dessus, **à sauvegarder avec la base** (ADR-0044, `SECURITY.md`, runbook `docs/runbooks/cle-des-secrets-des-services.md`). Clé absente, fausse ou inutilisable : l'agent démarre, dit que les secrets sont illisibles, ne détruit rien. Un manifeste scellé par révision authentifie l'ensemble des champs (retrait/ajout/permutation = « altérée »), une clé illisible refuse d'écrire une révision sans secret par-dessus des secrets et de purger, et la reprise des opérations au démarrage n'empêche jamais l'agent de démarrer (journal illisible = « à vérifier »). Tout geste long ou destructif passe par le journal des opérations (`service_ops`, `service_op_steps`, ADR-0045) : `intent` durable AVANT le geste, `done` après ; au démarrage `domain::ops::recover` classe (jamais de reprise ni de relance), seuls les objets créés par l'opération sont retirés (inode revérifié). Un secret descellé reste un `Secret` : aucun `Debug`, aucune trace, aucun message d'erreur, aucun octet du fichier de base ni de son journal (test sentinelle `tests/service_spec_secrets.rs`). Migration `0012` (la `0011` est celle des services adoptés). **Branché par HRT-144** (ADR-0045, `BR-OPS-001` à `008`, `docs/open-api/service-ops.md`) : `GET /operations/services/{id}` (tout compte, mais une opération sur un service que le compte ne voit pas est `404 OPERATION_NOT_FOUND` comme une inconnue), `DELETE /operations/services/{id}` (acte `OperationCancel` `0x10`) et `POST /operations/services/{id}/decision` (acte `OperationDecide` `0x1D`, le choix est signé) exigent le droit « gérer les services » et la confirmation ; la réussite s'écrit au journal d'activité sous l'action du GENRE de l'opération, dans la transaction du changement (`ServiceOpTx`), un refus sous `operation.cancel` / `operation.decide` ; l'écriture d'une ligne du journal d'étapes vérifie le statut dans sa propre instruction (`StepGuard`). Message `operation` du sujet `services` (cadence 500 ms par opération et par connexion, état final jamais perdu), `ServiceItem.busy` / `last_action` projetés du journal (`OpsIndex`), capacité `service-ops`. La reprise au démarrage compte les conteneurs du service dans le vrai moteur (`EngineObserver`, lecture seule) ; `UnobservedState` ne sert plus qu'aux tests. Les actes `0x0C` à `0x10`, `0x14`, `0x19`, `0x1B`, `0x1D`, `0x1E` et les codes d'erreur des tranches L1 à L3 sont déclarés d'un coup (`ActKind::DECLARED_WITHOUT_ROUTE` : ceux sans route). Tests bridés : `cargo test -p hearth-agent -j 2 --test service_ops_https --test service_ops_observer -- --test-threads=2` ; ensuite : `cargo test -p hearth-agent -j 2 --test service_spec_secrets --test service_ops_journal --test migration_0012 -- --test-threads=2` et `--lib ops sealed spec drift`. Règles `BR-EDIT-031`, `034` à `036`, `BR-LIFE-013`, `BR-DEL-019`, `BR-JEU-006`.

## Démarrer, arrêter, redémarrer un service (HRT-64)

`POST /services/{key}/start`, `/stop` et `/restart` (actes `0x0C`, `0x0D`, `0x0E`, actes de pilotage : le mot de passe suit l'état de confiance que l'agent juge à l'acte, HRT-194, `hearth_proto::admin_act::password_need`, BR-LIFE-016 ; `Access::Services`) répondent `202 { action_id, grace_s }` : `ServiceLifecycle::request` (`application/service_lifecycle.rs`) juge SANS rien attendre du moteur (moteur prêt, service publié, action en cours, état permis par `domain::ops::check_state`), accepte une opération du journal (verrou exclusif, plan d'UNE étape non destructive, donc `interrupted` « résultat inconnu » après une coupure de l'agent, jamais « à vérifier ») et lance l'exécution en tâche de fond. **Le pilote est fixé par la clé** : `u_<unité>` → `ServiceSupervisor::{start, stop, restart}` (`systemctl <verbe> -- <unité>`, jamais le moteur), sinon `ContainerEngine::{start, stop(délai), restart(délai)}`. **L'arrêt voulu est écrit dans `service_intents` AVANT l'ordre** (`ServiceIntents`, `SqliteServiceRepo`) ; le registre s'en sert (`honour_stop_request`) pour qu'une sortie non nulle voulue ne soit pas « En erreur », et montre « Arrêt en cours » / « Démarrage » pendant l'action (`overlay_transition`, jamais « En marche » par avance). L'attente est `max(délai d'arrêt + 30 s, 60 s)` (`LifecycleTimings::wait_for`), un dépassement est `interrupted`/`timeout`, jamais rejoué. Les démarrages demandés par Hearth sont exemptés du compteur « redémarre en boucle » (`StartWindow::exempt`). Après la fin de l'action, une surveillance de 10 s (démarrage) ou 30 s (arrêt) pose, après coup et une seule fois, `stopped_right_after_start` ou `restarted_by_host` sur l'opération (`OpJournal::annotate_cause`) et au journal d'activité ; elle ne bloque rien. Une action interrompue par un redémarrage de l'agent est consignée au démarrage (`record_interrupted`). Causes : `domain::ops::Cause` (listes jumelles `OperationCause` du fil et `Reason` du journal d'activité). Aucun texte du moteur, aucune variable, aucune commande dans une erreur, une trace ou le journal. Moteur : `EngineError::PortInUse` reconnu dans le texte par `infrastructure/engine/errors.rs`, jamais exposé. Tests bridés : `cargo test -p hearth-agent -j 2 --test service_lifecycle_https --test service_intents_repo --test engine_fake --test engine_fake_daemon -- --test-threads=2` ; `--lib domain::ops application::service_lifecycle application::services` ; les ordres `systemctl` (faux `systemctl`, `cfg(unix)`) : `--test supervisor_proc` ; le vrai moteur et le vrai systemd : job `engine` de la CI (`engine_real.rs` section `writes`, `engine_supervised.rs`). `deploy/e2e/admin_act.py confirm-service {start|stop|restart}`. Règles `BR-LIFE-001` à `025` (sauf 007, 008, 013, 017, 020, 022 : client ou socle), `BR-SVC-004` à `006`, `015`.

## Déployer une image (HRT-68)

`POST /deployments` (acte `ServiceDeploy` `0x0F`, jamais couvert par l'élévation, droit « gérer les services ») répond `202 { operation_id, service_key }` : `Deployments::deploy` (`application/deployments.rs`) juge SANS rien attendre du moteur (moteur prêt, plan fermé `domain::services::deploy::validate`, **limites de mémoire et de processeur obligatoires** `LIMITS_REQUIRED`, nom libre, ports libres ou réservation cochée, deux déploiements au plus, espace disque), accepte l'opération `deploy` (verrou de la clé, nom réservé), écrit la description durable (révision 1, secrets scellés, ADR-0044) puis lance l'exécution en tâche de fond : `check`, `pull` (progression, annulable par `DELETE /operations/services/{id}`), `create` (point de non-retour : le conteneur est créé DEPUIS la description relue en base, par l'unique constructeur de plan `domain::services::plan::plan_from_spec`, plan FERMÉ sans champ privilégié), `start`, `watch` (10 s). **Un échec avant le lancement ne laisse rien** (description, dossier de données, conteneur). **Un conteneur n'est « créé par Hearth » que si son identifiant est consigné dans `service_containers`** (migration `0015`, `ServicesRegistry::register_hearth_container`) : l'étiquette ne prouve rien. Le déploiement en cours est une ligne `deploying` du registre (`begin_deploying`). Dossiers gérés : `<données>/services/<clé>/<chemin aplati>/` par `SafeFs`, montés en `Mounts` de type `bind` (jamais `Binds`) ; un « autre dossier du serveur » est refusé (`FOLDER_REFUSED`, HRT-70). `POST /deployments/check` est une consultation sans secret ni journal ; `GET /engine/capacity` donne les bornes de la machine. Récupération d'image : port `ContainerEngine::{image_present, pull, create, remove, info}`, erreurs typées par `infrastructure/engine/errors.rs::{translate_pull, translate_create}` (table de textes enregistrés, confirmée par le job `engine`). Valeur et nom de variable, commande : `Secret`, jamais tracés, journalisés, signés (test sentinelle `tests/service_deploy_https.rs`). ADR-0039, règles `BR-DEPLOY-*` (001 à 009, 014, 016 à 021, 023 à 027, 030, 032 à 035, 037, 038). Tests bridés : `cargo test -p hearth-agent -j 2 --test service_deploy_https --test engine_fake --test engine_fake_daemon -- --test-threads=2` ; `--lib domain::services application::deployments infrastructure::engine` ; vrai moteur : job `engine` (`engine_real.rs`, contrat `deploys` et redémarrage du démon).

## Fiches de serveur de jeu (HRT-113)

Format de fiche version 2 dans le DOMAINE de l'agent (`crates/hearth-agent/src/domain/catalog/`, [ARCHITECTURE.md](crates/hearth-agent/src/domain/catalog/ARCHITECTURE.md)), fiches embarquées dans `crates/hearth-agent/catalog/<id>/` (`fiche.toml`, `settings.toml`, `ids.lock`). `build.rs` applique le chargeur réel et fait échouer la compilation d'une fiche refusée. `cargo xtask catalog-check [--release]` : chargeur réel + `ids.lock` (un réglage ne disparaît pas par oubli, ne change pas de clé sans `rename`, n'est pas réutilisé) ; `--release` (option, branchée sur aucune publication) refuse toute fiche `preview` et dit si sa mémoire recommandée manque ou n'est qu'une mesure au repos (HRT-122, BR-RES-038) ; sans l'option, la CI le lance à chaque PR (job `rust`). Toute fiche est embarquée, `preview` comprise, mais seule `embedded::keep_offered` (fiches `published`, plus les `preview` dans une construction d'essai : variable de construction `HEARTH_PREVIEW_FICHES`, refusée par `cargo xtask agent --release`, HRT-101) est proposée à l'application. Tests bridés : `cargo test -p hearth-agent -j 2 --lib catalog -- --test-threads=2`. Règles `BR-FICHE-005` à `011`, `037`, `038`, `046` à `049`, `BR-RES-031` à `033`, `038`, `BR-JEU-002`, `038` à `040` ; décisions ADR-0050 à ADR-0052 ; ce qu'une fiche peut et ne peut pas demander : `SECURITY.md`. Le validateur du déploiement ordinaire (HRT-68, `domain::services::deploy::OrdinaryDeployment`) est branché sur la traduction (HRT-101, `domain::services::from_fiche`) : toute traduction est acceptée par lui (`tests_translate.rs`, test de propriété à graine fixe).

## Catalogue et installation depuis une fiche (HRT-101)

`GET /catalog` et `GET /catalog/{id}` (tout compte authentifié, capacité `catalog`, `application/catalog.rs`) rendent les fiches de CETTE construction, avec l'empreinte et la preuve de chaque chiffre de ressource ; une fiche écartée au chargement est comptée (dossier, invariant) et consignée une fois au démarrage (`catalog.fiche.refused`, auteur : le système). **Installer** : `POST /deployments` avec un membre `source` (`{ type: "fiche", id, version, digest, variant?, answers, agreements, ports, optional_ports, world_imported }`) à la place de `image`, `env`, `ports`, `mounts`, `command` (qui doivent être vides). C'est le MÊME acte `0x0F`, le même droit, la même confirmation, la même opération : `FicheInstaller::prepare` (`application/fiche_install.rs`) vérifie la fiche proposée et son empreinte (`FICHE_UNKNOWN`, `FICHE_CHANGED`), les réponses (`SETTING_REFUSED` : réglage, raison, au plus UN caractère, jamais la valeur), les contrats (`AGREEMENT_REQUIRED`, même client modifié), tire les secrets de la fiche par le port `SecretRandom` (scellés sous `gen-<id>`), traduit, fait juger par `OrdinaryDeployment`, exige les limites, puis `fit` (`HOST_TOO_SMALL` et `NO_SPACE` pour un chiffre MESURÉ seulement ; un chiffre de l'éditeur demande la case `accept.low_disk`). Le fichier de réglages produit est écrit par `SafeFs` dans le dossier géré AVANT la création (image root : `0600` root, sinon `0640` au propriétaire de la fiche), le conteneur est créé par l'empreinte de l'image quand la fiche en a une. La description garde variante, réponses (les secrètes scellées), questions figées et contrats (`SpecFiche`, dans `spec_json`, sans migration). Journal : `service.deploy`, cible `Target::GameInstall`, jamais une valeur. Phases du jeu (`GamePhases`, en mémoire, signe « prêt » littéral vu après le lancement) : `begin` est branché au démarrage de l'installation, mais `refresh`, `forget` (suppression d'un service, HRT-85) et la projection dans la liste des services n'ont pas encore d'appelant (suivi : HRT-197). Tests bridés : `cargo test -p hearth-agent -j 2 --test catalog_https --test fiche_install_https --test fiche_install_secrets --test game_phase -- --test-threads=2`. Règles `BR-FICHE-001` à `004`, `012`, `013`, `016` à `032`, `035`, `036`, `056`, `058` ; décisions ADR-0050 (amendée), ADR-0054 (contrat). OpenAPI : `docs/open-api/catalog.md`, `docs/open-api/services.md`.

## Réglages d'un serveur de jeu (HRT-108)

`GET /services/{key}/settings`, `POST /services/{key}/settings/analyze` et `PUT /services/{key}/settings` (acte `GameSettingsSave` `0x1E`, couvert par l'élévation ; niveau `Services`, capacité `game-settings`, `docs/open-api/game-settings.md`, ADR-0051). `application/game_settings.rs` (`GameSettings`) : le fichier du jeu est lu et écrit par `SafeFs` (2 Mio au plus), retouché sur les seules valeurs demandées (commentaire, ligne inconnue, ligne commentée gardent leurs octets) et jamais écrit si aucun octet ne change ; un fichier réécrit par le jeu rend des `drifts` et l'enregistrement exige un choix par réglage (`keep_file`, `keep_mine`) sinon `SETTINGS_FILE_CHANGED` sans rien écrire ; un fichier illisible est refusé entier (`SETTINGS_FILE_UNREADABLE`) ; les changements sont jugés tous ou aucun ; un réglage `env` ou `args` demande une recréation (`RECREATE_NOT_AVAILABLE` tant que HRT-87 n'est pas livré) ; l'effet signé est recalculé (`SETTINGS_CONFLICT`). Les valeurs voulues sont en base (migration `0016`, `game_settings` : révision numérotée, empreinte du fichier ; `game_setting_secrets` : secrets changés, scellés, révision 0) ; l'agent ne redémarre rien (BR-JEU-035). Un secret reçu n'est ni dans une vue, ni dans un `Debug`, ni dans le journal, ni dans la base en clair (tests sentinelles `tests/game_settings_https.rs`). `recreate_missing_files` est fournie mais pas encore appelée au démarrage d'un service. **Cibles de test partagées** : le hachage de compilation de `hearth-proto` est le même dans tous les arbres de travail (même chemin relatif) : dans un `CARGO_TARGET_DIR` partagé, `touch crates/hearth-proto/src/lib.rs` avant de compiler si une erreur dit qu'un module de `hearth_proto` manque. Tests bridés : `cargo test -p hearth-agent -j 2 --test game_settings_https --test game_settings_use_cases --test migration_0016 -- --test-threads=2` ; `--lib catalog::tests_io`. Règles `BR-FICHE-042`, `044`, `046` à `048`, `052`, `053`, `BR-JEU-035`, `036`.

## Onglet Réglages d'un serveur de jeu (HRT-109)

Client : onglet « Réglages » (`?onglet=reglages`, `GameSettingsTab`) d'un service né d'une fiche, et « Voir tous les réglages » (`InstallSettings`) dans l'installation ; règles pures `apps/desktop/src/settings/` ([ARCHITECTURE.md](apps/desktop/src/settings/ARCHITECTURE.md)). `GET /catalog/{id}` sert maintenant `themes` et `settings` (le catalogue complet : contrôle, nom technique, thème, niveau, défaut du jeu, version ; `application/catalog.rs::setting_view`) : le client n'invente ni libellé, ni borne, ni choix. Liaison `hearth-link/src/manager/game_settings.rs`, coquille `service_ops/game_settings{,_dto}.rs` (commandes `read_game_settings`, `analyze_game_settings`, `save_game_settings` ; refus lus par code), genre d'acte `game_settings_save` (élévation). Le client ne redémarre rien lui-même : la case « Redémarrer maintenant » (décochée) demande la confirmation habituelle de `service_restart`. ## Arrêter un serveur de jeu en enregistrant son monde (HRT-103)

Pour un service créé depuis une fiche, `stop` et `restart` (mêmes actes `0x0D`, `0x0E`) suivent ce que la fiche déclare (ADR-0052, `BR-JEU-001`, `002`, `003`, `005` à `009`, `011`, `016`, `025` à `027`, `032`, `034`, `038`, `042`) : `application/game_stop.rs` (`GameStop::{lookup, run}`) déroule la suite bornée de la fiche (ordres littéraux écrits sur l'entrée du service par `ContainerEngine::send_stdin_line`, seule écriture du port hors cycle de vie, attente d'un signe LITTÉRAL dans les journaux postérieurs à l'ordre, pause), puis l'ordre de sortie et AUSSITÔT l'arrêt demandé au moteur (sinon `unless-stopped` relance le jeu). `ServiceLifecycle::run_game` lui rend les deux moments irréversibles (`StopMoments` : arrêt voulu écrit AVANT l'ordre de sortie, retiré si la décision est « Annuler »). Une suite `untested`, un ordre refusé, un signe obligatoire non vu, une fiche inconnue : **rien n'est arrêté**, l'opération attend `continue` (« Arrêter quand même ») ou `cancel` ; 15 minutes sans réponse : `cancelled`, le service reste en marche, verrou rendu. Un service adopté ou supervisé par une unité ne reçoit jamais d'ordre. Les étapes du plan (`save_world`, `stop`, `start`, `domain/ops/game_stop.rs`) ne sont pas destructives : un redémarrage de l'agent classe l'opération « interrompue », rien n'est rejoué. Le journal d'activité nomme ce qu'il est advenu de l'enregistrement (`SaveMention`), jamais le texte d'un ordre. **Aucune route ne porte `send_stdin_line`** (garde `architecture_guard.rs::no_route_carries_the_order_written_to_a_games_input`) ; aucune commande n'est exécutée dans un conteneur. `GET /services/{key}/game-secret` (niveau `Services`, capacité `game-services`) rend le mot de passe saisi du serveur, descellé de la description (`GameSettings::reveal_game_password`), consigné AVANT la valeur sous `service.game.password.reveal`, jamais la valeur. Limites : le signal d'arrêt de la fiche (`SIGTERM`, `SIGINT`) n'est pas posé à la création du conteneur (le plan fermé n'a pas ce champ) ; l'essai réel de `send_stdin_line` (attache sans terminal, `unless-stopped` après `exit`) est le test `engine_real.rs` du job `engine` de la CI. Tests bridés : `cargo test -p hearth-agent -j 2 --test game_stop_https --test game_settings_use_cases -- --test-threads=2` ; `--lib domain::ops::game_stop`. OpenAPI : `docs/open-api/game-services.md`.

## Lecture d'une archive hostile (HRT-130)

Un seul module lit une archive `.zip`, `.tar` ou `.tar.gz` venue d'ailleurs : `crates/hearth-agent/src/domain/archive/` ([ARCHITECTURE.md](crates/hearth-agent/src/domain/archive/ARCHITECTURE.md), ADR-0055, règles `BR-ARCH-001` à `011`). `inspect` juge TOUTE l'archive sans rien écrire ; `extract` recalcule l'empreinte, refuse si elle a changé, puis écrit par le port `ExtractSink` (adaptateur `infrastructure/archive_fs.rs`, tout par descripteur depuis le dossier parent de la destination, qui doit appartenir à l'utilisateur effectif de l'agent et n'être inscriptible que par lui ; dossier d'attente puis `renameat2` sans remplacement ; jamais un lien suivi ; hors Unix, écrire est refusé). Aucune fonction d'extraction d'une crate (`unpack`, `extract`) : lecteurs de zip et de tar écrits à la main sur `flate2`. Toute nouvelle entrée du format passe par un test à archive fabriquée (`testkit.rs`), jamais un binaire versionné. Tout ce qui écrit (`tests/archive_fs.rs` module `unix`, `infrastructure/archive_fs/tests_unix.rs`) ne tourne qu'en CI Linux ; sur le poste Windows, vérifier la compilation Linux par une copie isolée (`cargo clippy --target x86_64-unknown-linux-gnu --all-targets` sur les seuls fichiers de l'archive, contre le `rustix` du verrou), le reste du crate exigeant un compilateur C croisé (`ring`). Tests bridés : `cargo test -p hearth-agent -j 2 --lib archive -- --test-threads=2` et `--test archive_fs`.

## Fichiers d'un service (HRT-145)

Tout accès aux fichiers du dossier d'un service passe par le port `SafeFs` (`application/ports/safe_fs.rs`, adaptateur `infrastructure/fs/`, `RelPath` dans `domain/files/`, ADR-0046, règles `BR-DEPLOY-010`, `BR-FILES-003`, `BR-FILES-004`, `BR-DEL-007`, `BR-DEL-009`) : racine `<données>/services/<clé>/` ouverte une fois, chaque composant ouvert par `openat(O_DIRECTORY | O_NOFOLLOW)` depuis le descripteur du précédent, aucun lien suivi, aucun montage franchi, écriture atomique, retrait par descripteurs. Aucun `std::fs` sur un chemin composé sous cette racine. Les pièges (liens vers l'extérieur, tubes, courses) ne se jouent que sous Linux : `infrastructure/fs/tests_unix.rs` et `tests/safe_fs.rs` (suite de contrat contre le faux `FakeSafeFs` et le vrai). Vérification Linux depuis Windows : WSL, copie isolée des seuls fichiers du module (même méthode que pour l'archive).

## Mise à jour de l'agent depuis le client (HRT-17, lot interface)

Le CLIENT lit la cible de l'agent dans la section `agent` du manifeste de versions (ADR-0021, ADR-0035), dans la MÊME requête que son propre flux (`version_comparator` du greffon) : toujours UNE requête par vérification (BR-UPDATE-001). Règles `BR-UPDATE-020` à `023`.

### Dépôt d'une version (HRT-51)

```sh
cargo xtask release-stage --client-dir <artefact publish-client> --agent-binary <hearth-agent> --agent-signature <hearth-agent.minisig> [--install-script <autre fichier>]
cargo xtask release-upload             # ESSAI À BLANC (défaut) : affiche chaque écriture, ne lance ni aws ni curl (seul git, en lecture)
cargo xtask release-upload --confirm   # dépose : fichiers de la version, relecture publique, script, manifeste EN DERNIER (chacun relu dans le bucket)
```

`release-stage` refuse AVANT toute écriture un arbre qui n'est pas son commit (HRT-60, BR-RELEASE-003) : fichier SUIVI modifié (indexé ou non, `git status --porcelain --untracked-files=no`), fichier NON SUIVI et non ignoré sous les entrées de la construction de l'agent (`Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo`, `.sqlx`, `crates` : une migration ou un `build.rs` non suivi entre dans le binaire), fichier IGNORÉ sous ces mêmes chemins (l'ignorance peut venir de `.git/info/exclude` ou du fichier d'exclusion global, locaux au poste), fichier masqué à git (`skip-worktree`, `assume-unchanged`, vus par `git ls-files -v`). Les autres fichiers non suivis (`target/`, artefact du client, signatures) sont tolérés ; un `git` muet n'est jamais lu comme « propre ». Il nomme les fichiers (dix au plus), lit `HEAD` (relu une fois pour le script et comparé, le script étant lu par `git show <ce commit>`), l'affiche et l'écrit dans `target/release-stage/COMMIT`, à côté de `releases/` (jamais déposé, hors de la liste fermée). `release-upload`, essai à blanc compris, refuse si ce fichier manque ou si le commit ou l'arbre en place ont changé (seul git, en lecture, tourne avant le premier `aws` ou `curl`). Le binaire donné par `--agent-binary` doit avoir été construit sur ce commit : `cargo xtask agent` écrit, à côté de `target/dist/hearth-agent`, `hearth-agent.build` (quatre lignes `commit=`, `tree=clean|dirty|unknown`, `sha256=`, `version=`, `clean` seulement si l'arbre est propre avant ET après la construction, sur le même commit) et `release-stage` refuse un binaire sans enregistrement, de somme différente, d'un autre commit que `HEAD` ou construit sur un arbre pas propre (aucune option de contournement ; l'enregistrement n'est jamais assemblé ni déposé). `cargo xtask agent` affiche le commit construit et avertit si l'arbre n'est pas le commit, sans refuser (la commande sert au développement et aux tâches e2e ; un git qui échoue n'y fait pas échouer la construction). Limites : l'enregistrement est un fichier en clair, falsifiable à la main (garde contre l'erreur, pas contre la malveillance) ; le contrôle de l'arbre est fait à l'assemblage et au dépôt, avec de petites fenêtres entre ses lectures et celles de `Cargo.toml` et des clés ; l'installateur du client est relié à ce commit par son enregistrement `.build` (HRT-173, ci-dessous) ; l'image du conteneur est figée par empreinte, mais les paquets `apk` et les volumes de cache de Cargo ne sont pas vus par cette garde ; rien ne vérifie que `HEAD` est le commit qui sera étiqueté. `release-stage` écrit sous `target/release-stage/` seulement, après avoir revérifié signatures (client et agent avec version signée), sommes, adresses, liste fermée de l'API, forme du manifeste et script (non vide, `#!/bin/sh`, lit `releases/latest/agent`) ; la version est celle du dépôt, l'agent est rangé dans le dossier de SA version. Sans `--install-script`, `deploy/install.sh` doit être identique à `HEAD` et ce sont les octets de `HEAD` (`git show`) qui sont déposés, pas ceux du disque (le commit est affiché) ; si l'option désigne ce même fichier du dépôt, la même garde s'applique. `--install-script` ne sert que pour un AUTRE fichier (lu sur le disque, non comparé à `HEAD`). `release-upload --confirm` exige l'outil `aws` (AWS CLI v2) et `curl`, et les variables `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` de la clé de publication dans l'environnement (lues par `aws`, jamais par `xtask`, jamais en argument) ; il refuse d'écrire une clé de version déjà présente avec un autre contenu, et de remplacer un manifeste en place de version supérieure (sauf `--allow-rollback`, qui laisse une ligne « RETOUR ARRIÈRE » avant la première écriture). Chaque objet part des octets vérifiés en mémoire (`aws s3 cp -`). Droits requis de la clé de publication : LECTURE d'objet (`HeadObject`, `GetObject`) et ÉCRITURE (`PutObject`, dépôts en plusieurs parties compris), SANS suppression ; sans droit de lister, une clé absente peut répondre 403 au lieu de 404 : l'outil s'arrête alors (« état impossible à établir »), à vérifier à la console avant le premier dépôt. Règles `BR-RELEASE-001` à `003`, code `xtask/src/release_stage.rs` et `release_publish.rs`.

**Contrôles préalables (HRT-172)** : `cargo xtask release-preflight [--versions-only]` (`xtask/src/release_preflight.rs`, mode GitHub dans `xtask/src/ci.rs`) refuse AVANT toute construction, dans l'ordre : une branche autre que `main` (`HEARTH_REF`, BR-RELEASE-004) ; des numéros qui ne concordent pas dans `Cargo.toml` (source), `Cargo.lock` (cinq paquets), `apps/desktop/package.json`, `package-lock.json` (racine et `packages[""]`), avec AUCUN `version` dans `tauri.conf.json` (BR-RELEASE-006) ; des notes vides ou de plus de 2000 caractères (`HEARTH_NOTES`) ; une clé publique de développement (client ou agent) ; un `HEAD` qui n'est pas `HEARTH_SHA` ; une version déjà publiée (manifeste public ET release GitHub), annoncée sans release, ou une étiquette/release sans manifeste qui l'annonce (BR-RELEASE-008). Les lectures passent par `Host` (`curl`, `git ls-remote`), par code HTTP exact : une absence ne se déduit jamais d'un texte d'erreur, un manifeste illisible (défi Cloudflare compris) est un arrêt ; le jeton `GH_TOKEN` passe par l'entrée standard de `curl`, jamais en argument. Sorties `version` et `commit` dans `$GITHUB_OUTPUT`, erreurs en annotation `::error` et dans le résumé quand `GITHUB_ACTIONS=true`. `--versions-only` (numéros et clés, sans réseau) tourne à chaque PR (job `rust` de `ci.yml`). Tests : `cargo test -p xtask -j 2 --bin xtask release_preflight ci -- --test-threads=2`. Runbook (messages et gestes) : `docs/runbooks/publier-une-version-du-client.md`.

**Constructions vérifiables (HRT-173, BR-RELEASE-007)** : le client et l'agent d'une version sortent du MÊME commit, sur un arbre propre, et le prouvent. `cargo xtask agent --release` (construction de publication ; sans l'option, la construction de développement avertit seulement) refuse un arbre qui n'est pas le commit AVANT et APRÈS la construction (`agent::refuse_unless_clean`, erreur), télécharge l'image du conteneur avec reprise (`agent::pull_image` : 5 essais, attente 5, 10, 20, 40 s, seulement limite de débit ou panne passagère, derrière `Host`) et exige `hearth-agent.build` (`agent::build_release`). `cargo xtask client-record --begin` (avant `npm ci`) puis `--installer F --version X.Y.Z` (après `tauri build`) écrivent `F.build` au format `BuildRecord` (`xtask/src/client_record.rs`) ; `release-stage` exige ce fichier ET celui de l'agent, de somme égale au fichier, de commit égal à `HEAD`, d'arbre `clean` (`release_stage::check_client_build` / `check_agent_build`), jamais assemblés ni déposés. `cargo xtask agent-sign --binary F --version X.Y.Z --out S` signe l'agent avec `HEARTH_AGENT_SIGNING_KEY` et son mot de passe OBLIGATOIRE `HEARTH_AGENT_SIGNING_KEY_PASSWORD` (`xtask/src/agent_sign.rs` ; type `Secret`, `xtask/src/secret.rs` : jamais en argument, jamais dans une trace, une erreur ou un `Debug`, test sentinelle), commentaire signé `version:X.Y.Z`, relue contre `update-key.pub`. La racine du dépôt n'est définie qu'à un endroit (`xtask/src/repo_root.rs::repo_root`) et `cargo xtask ci-root-check` (et la tête de `client-sign`, `client-manifest`, `agent-sign`, `release-stage`, `release-upload`) refuse en environnement GitHub une racine compilée qui n'est pas `$GITHUB_WORKSPACE`. Tout se teste par faux (`Host`, `TreeFake`, `DockerFake`) : ni Docker, ni réseau, ni clé réelle. Tests : `cargo test -p xtask -j 2 -- --test-threads=2`. Les enregistrements sont des fichiers en clair : garde contre l'erreur, pas contre la malveillance. Le job `build` de `publish-client.yml` appelle `client-record --begin` avant `npm ci` et `--installer` après `tauri build` : le `.build` voyage avec l'installateur jusqu'à l'artefact `hearth-client-signed`. Pour le client, les fichiers NON SUIVIS sont cherchés sous les entrées de l'agent ET sous `apps/desktop` ; les IGNORÉS seulement sous les entrées de l'agent et sous `apps/desktop/.env*` (fichiers d'environnement de vite ; `node_modules`, `dist` vivent ignorés sous `apps/desktop`). L'installateur doit être plus récent que le relevé `--begin` (dates de modification). Le relevé de `--begin` ne sert qu'une fois, réussite ou échec : après un refus il faut tout reconstruire depuis `--begin`.

**Reprise, release GitHub, essai à blanc (HRT-174, BR-RELEASE-009 à 011)** : `release-upload` répond par les messages exacts de la spec (première ligne ; le détail technique suit, et en mode GitHub la première ligne seule devient annotation et résumé, `main.rs`) : fichier déjà déposé avec un autre contenu (`refuse_different`), dépôt interrompu avant le manifeste (`interrupted` : `n` fichiers écrits ou reconnus sur `total`, et la version que les utilisateurs voient encore), essai à blanc (`dry_run_report`) ; `--confirm` lance d'abord `aws --version` (majeure 2 exigée, `check_aws_version`). `cargo xtask release-github --notes-file F [--stage-dir D]` (env `HEARTH_SHA`, `GH_TOKEN` ; `xtask/src/release_github.rs`) crée l'étiquette et la release `vX.Y.Z` en ne faisant que ce qui manque (table `decide`), s'arrête sur une étiquette qui pointe un autre commit, relit la release puis le manifeste public. `client-manifest` sans `--notes-file` prend `HEARTH_NOTES` (écrit `notes.txt` à côté de `--out`) et sans `--date` la date UTC du moment. Tests : `cargo test -p xtask -j 2 -- --test-threads=2 release_github release_publish client_release`.

**Flux de publication (HRT-175, BR-RELEASE-004, 005 et 011)** : `.github/workflows/publish.yml` (« Publier une version », `workflow_dispatch` seul, entrées `essai` cochée par défaut et `notes`) enchaîne `preflight`, `build-client`, `build-agent`, `review`, `publish` (environnement `release`, seul job à secrets, chacun dans l'`env:` de son étape) et `release-github`. La logique est dans `xtask`, le YAML n'enchaîne que ; aucun cache, AWS CLI épinglée par version et SHA-256, actions épinglées par SHA, aucune entrée du formulaire dans un `run:`. `xtask/src/workflow_check.rs` (tests seulement) lit le fichier comme du texte et refuse tout écart (un changement de forme du fichier fait échouer les tests, c'est voulu) : `cargo test -p xtask workflow_check`. L'environnement `release` et ses six secrets sont des réglages GitHub du propriétaire (runbook `publier-une-version-du-client`). `publish-client.yml` reste jusqu'à HRT-176.

## Règles

- Architecture hexagonale dans `hearth-agent` et `hearth-link` : `domain/` sans E/S ni dépendance vers axum, SQLx, système. Ports dans `application/ports/`.
- Une règle métier vit dans `domain/` et a sa fiche `docs/business-rules/BR-*.md`, modifiée dans le même commit.
- `unwrap` et `expect` interdits hors tests (lint en erreur). Erreurs : `thiserror` par couche, pas d'`anyhow` ; l'erreur fatale est journalisée une seule fois dans `main`.
- Un port est consommé par la racine de composition (`app.rs`) via `Arc<dyn Port>` ou `&dyn Port`, jamais par son type concret. `application` ne connaît ni axum ni SQLx ; `entrypoint` n'importe pas `infrastructure`. Mots de passe et hachés : type `Secret`, jamais dans un message ou un journal.
- `hearth-proto` : aucun type de framework, aucune E/S.
- Le client ne parle à l'agent que par `hearth-link`. L'interface web n'ouvre aucune connexion réseau.
- Interface (`apps/desktop/src`) : Composition API et `<script setup lang="ts">`, Atomic design, zéro `style=` en ligne, SVG en composants atomes, jetons CSS uniquement (`styles/tokens.css`), textes dans `i18n/fr.ts`.
- Textes d'interface : français, vouvoiement et impératif (règle de Voiky depuis le 14/10), phrases complètes, jamais de tiret cadratin.
- Git : une branche par ticket (`feat/HRT-nn-slug`), PR, pas de push direct sur `main`. Gel des commits en heures ouvrées (voir hub).
